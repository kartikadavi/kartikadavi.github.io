Evidence-Driven AI Workflow & Governance Platform

I designed and directed an AI-assisted workflow that discovers relevant roles, evaluates fit, maps job requirements to verified career evidence, and generates tailored resumes. Rather than trusting a model to produce a polished answer, the system verifies source information, validates generated claims, and uses an independent LLM judge for advisory quality assessment.

Applied AI engineering · LLM evaluation · AI governance · Workflow orchestration · Cost optimization · Human-in-the-loop controls · Continuous improvement.

The problem

Job search and resume tailoring involve the same repetitive work, role after role: discover openings, evaluate fit, map requirements to what you can actually prove, customize the resume, and check the result. Done by hand, the quality checks are the first thing to slip — and a polished resume with an unsupported claim is worse than no resume at all.

What usually breaks

Generative tools write confident, fluent resumes. Fluency is not evidence. Without a check that ties every number back to a source record, the output drifts — invented metrics, overstated scope, tools never used.

What this system does instead

It treats the resume as a governed artifact: evidence first, generation second, and an independent judge that never sees the evidence bank — so it can only score what the resume itself proves.

How it works

Five stages, one role at a time. Two controls run across every stage: governance (traceability, groundedness, human oversight, version control) and cost engineering (free-tier-first routing, caching, token discipline, fallbacks).

The diagram is the portfolio-facing view: a recruiter or hiring manager should understand the system in under a minute. The operational version adds intake gates, fix rounds, and the judge fallback chain — the controls below describe those.

What each stage does

1 · Job Intelligence

Roles are discovered from career sites and feeds, then the posting itself is verified against the official source — title, live status, date, sponsorship, and location — before any work starts. A build never begins on an unverified posting.

2 · Fit & Evidence

Each requirement is mapped to the evidence bank as Direct, Transferable, or Gap. Direct evidence leads; transferable evidence is framed honestly, translating the mechanism without implying processes never used; gaps stay visible, never keyword-papered.

3 · Grounded Generation

The resume is drafted from the evidence map, with direct relevance first and one primary metric per bullet. Every claim must trace to a source record — an unbanked claim is flagged and rewritten to the strongest defensible version.

4 · AI Quality Assurance

Deterministic checks come first: grounding (every number traced), mechanical gates (unsupported numbers, banned formats, weak openers, tense, owned tools), and a 13-point audit. Then an independent LLM judge scores fit, relevance, clarity, ATS alignment, groundedness, and risk — advisory only, never a blocker.

5 · Delivery & Learning

The audited resume is exported, synced, and tracked. Gaps, flags, audit findings, and judge results are reviewed weekly; recurring issues are classified and fixed through controlled changes with regression checks before they are promoted.

The ship rule

A failed gate goes to a fix round — at most two. After two rounds, the strongest version ships with its findings recorded as flags. There is no blocked, no-output terminal state. Human judgment is the final gate: nothing is submitted without my review and my click.

Models used, in general

The chain is free-tier-first by design. Cost was a constraint from the start, not an afterthought — so the architecture routes to usable free-tier capacity before any paid inference, and falls back when a model hits a limit or returns an invalid response.

Primary judge · Gemini 2.5 Flash (free tier)

The independent judge. It scores the audited resume against the job description on a fixed rubric. It never sees the evidence bank or the build notes — it can only score what the resume itself proves. A different model family from the builder, so the judgment is independent of generation.

Fallback rungs · Groq, gpt-oss-120b / gpt-oss-20b (free tier)

If the primary judge errors, rate-limits, or returns an invalid response, the chain falls to Groq's open-weight models — 120b first, then 20b. Groq never retries a rate limit; the chain moves to the next rung, never loops. There is no OpenAI API anywhere in this chain.

Model availability, free-tier terms, and rate limits are provider-controlled and can change. The models above are the currently configured chain. No credentials, API keys, or endpoints are exposed on this page — or anywhere on this site.

Governance controls

Fabricated claims → evidence bank

Every number and claim traces to a source record. The grounding audit checks them all; unsupported claims are flagged, not shipped silently.

Wrong job info → official-source verification

The intake gate verifies the posting is live on the official source before a build starts. Mirrors and aggregators do not count.

Inconsistent judgments → stable rubric

The judge uses a byte-identical system rubric, versioned with the prompt. The role-specific context changes; the standard does not.

Outage or quota → bounded fallback chain

If the judge is unavailable, the audited resume ships and the skip is recorded. The judge is advisory — its absence never blocks a build, and its verdict never overrides the audit.

Silent regression → fixed regression set

Changes are tested against a fixed benchmark of conflict cases and end-to-end builds before promotion. A change that fails regression does not ship.

Automation overreach → human final gate

The system prepares; I decide. No application is submitted without my review and my click, and a declined recommendation stays declined.

Cost engineering — $0 to date

$0 total spend to date is a measured historical fact, not a promise. Free-tier terms are provider-controlled, so this is described as free-tier-first — not guaranteed zero-cost forever.

  • Free-tier-first routing. Usable free-tier model capacity is preferred before any paid inference.
  • Fallbacks, not retries. When a model hits a limit or returns an invalid response, the chain moves to the next provider rung instead of retrying.
  • Caching where supported. Stable prompt content is cached where the provider supports it, so repeated calls cost less headroom.
  • Token discipline. Reusable system instructions stay separate from changing role-specific context; judge calls are limited and never retried on rate limits.
  • Hosting is free too. This site runs on GitHub Pages — no hosting bill, no paid services anywhere in the chain.

Continuous improvement

The system improves by evaluation, not by retraining. No model weights are fine-tuned.

  • Failed builds, unsupported claims, evidence gaps, and human corrections are reviewed weekly.
  • Each issue is classified as a data, prompt, rule, retrieval, model, or workflow problem — then a controlled change is made and regression-checked before promotion.
  • What changed, why, and in which version is recorded, with a rollback path. A change that fails regression does not ship.

Measured results beyond cost are not published here until they are instrumented. I do not publish invented performance numbers — pass rates, build counts, and agreement scores appear only once they are captured from real runs.

Lessons learned

Judge the judge

An LLM judge can hallucinate — it has quoted lines that are not in the resume. Every finding is quote-checked against the resume before it is acted on. A score alone never changes a build.

Gates enforce the mechanical; humans judge the rest

Verification scripts fail only on mechanical violations. Judgment calls surface as warnings. Failing a resume on a judgment call is how a process blocks output instead of improving it.

Never a blocked state

Early designs had a terminal “blocked” outcome when gates failed. That was wrong — the operator's judgment is the final gate, so the strongest version ships with its findings as flags.

Cost shapes the architecture

Free-tier limits forced real design decisions: a bounded fallback chain, caching, token discipline, and a judge that runs once per build. The constraint made the system better, not just cheaper.
